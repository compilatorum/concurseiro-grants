# 🌱 Farcaster Commons Lab × Compilatorum GrantOS

> **An open experiment in collective intelligence, verifiable contributions and ecosystem funding.**

This repository is both:
1. the experimental workspace for the **Farcaster Commons Lab (IPIT)**; and
2. the operational funding hub for the **Compilatorum GrantOS** portfolio.

The central loop is:

`Interaction → Contribution → Evidence → Recognition → Funding → Reinvestment`

GrantOS extends that loop by matching each bounded work package to an appropriate capital source: grants, RFPs, bounties, research calls, quadratic funding, crowdfunding, accelerators, customer revenue or retroactive funding when an active program exists.

## ⚖️ Funding integrity

- A grant is not interchangeable with a bounty, donation, accelerator investment or customer contract.
- A funding application must name a bounded work package, output, acceptance test, budget and evidence plan.
- Public-good outputs and commercial services must be separated clearly.
- Shared costs require a documented allocation rule; no expense or deliverable is charged twice.
- Attention (views/reactions), contribution (accepted artifacts) and impact (external use) are measured separately.
- Reputation, utility credits and transferable tokens are separate instruments.
- Tokenization does not create liquidity, ownership, a payment entitlement or a promise of return by itself.
- Retroactive funding is pursued only where a current program explicitly supports it.

## 🧪 Experimental thesis

Can an open social conversation become a verifiable, reusable contribution to a public repository?

The original hypotheses remain:
- H1: structured conversation increases conversion into verifiable GitHub contributions.
- H2: recognition and utility incentives can increase recurring participation.
- H3: provenance and review evidence reduce verification friction.
- H4: published artifacts are reused by independent projects.

The experiment must publish limitations and negative results as well as successful outcomes.

## 🚦First operating cycle

1. Choose one small, externally useful issue.
2. Define its work package, estimate, acceptance criteria and evidence.
3. Publish it as a GitHub issue and invite contributors through Farcaster.
4. Review and merge the contribution.
5. Record evidence and update the funding ledger.
6. Use the resulting proof to qualify one suitable funding route.

Start with a no-token pilot. Add utility credits or transferable instruments only when the underlying work unit, rights and settlement logic are clear.

> **Filosofema:** We do not need one grant for every project. We need to decompose each project into verifiable units of value that can meet the right source of capital.
